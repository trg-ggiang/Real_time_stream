## Objective and findings

User reported the generic 409 text while scheduling. The supplied text alone cannot distinguish server conditions. Source inspection found two paths: invalid/past start or end-before-start, and attempting another session on a nonrecurring meeting which already has one. listSessions omitted recurrenceRule, so after reload the frontend treated it as unknown and offered scheduling even for a single-session meeting already in use.

## Completed changes

MeetingsService.listSessions now returns existing recurrence_rule and waiting_room_enabled as API metadata. The current frontend schedule visibility rule can therefore hide adding sessions when recurrenceRule is null and a session exists. No schema changes or relaxed scheduling limits.

createSession returns stable INVALID_SCHEDULE_TIME and SINGLE_SESSION_EXISTS codes for the two 409 cases. meetings-api.ts translates those codes to specific Vietnamese instructions rather than displaying the unrelated generic join-time/conflict message. Unknown errors keep the existing safe fallback.

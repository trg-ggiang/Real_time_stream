## Decisions and limits

The existing DB already separates recruitment campaigns from activities, so the
future activities UI will consume the recruitment API rather than duplicating
campaign content into a second activity row. Existing raw statuses are preserved
and mapped to `pending/approved/rejected` for display.

The migration intentionally changes the verified recruitment guards and adds
columns/tables/functions. It must be reviewed and applied once to development;
it has not been applied to the user's Supabase. Regression fixtures cover the
core recruitment constraints/guards and are not a full copy of the live DB.
No commit, push, UI implementation or notification delivery worker was performed.
